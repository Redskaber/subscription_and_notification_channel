# 能力模型的前沿定义与完整分析

**2026 年前沿的能力模型已经从“简单的资源权限管理”演化为一个多维度、多层次的理论体系，其核心由三个支柱构成：线性类型（资源唯一性的数学保证）、对象能力（OCap 安全模型）、能力效应（与效应系统的深度融合）——而你的语言设计中的能力模型应该成为这三个支柱的统一体，通过线性类型提供编译期安全，通过 OCap 模型提供运行时安全，通过能力效应提供与效应系统的无缝集成。**

### 2.2 能力模型的七个维度

| 维度 | 定义 | 边界 | 与其他空间的关系 |
|------|------|------|----------------|
| **定性** | 能力 = 线性资源 × 效应权限 | 不是普通的值/类型 | 与效应空间的交集 |
| **定位** | CapabilitySpace（拓展空间下） | 不在核心空间（核心只定义类型） | 编译器核心需要理解 |
| **职责** | 资源访问的编译期+运行时安全 | 不负责业务逻辑 | 与类型系统协作 |
| **能力** | 授予/传递/组合/撤销/检查 | 不能凭空创造 | 与效应系统协作 |
| **边界** | 能力的作用域和生命周期 | 不能跨越安全边界 | 与模块系统协作 |
| **权限** | 能力允许的操作集合 | 不能超越声明的能力 | 与线性类型协作 |
| **协同** | 能力在效应流形上的传播 | 需要效应系统的支持 | 与流形分析协作 |

## 三、能力模型的完整语言设计

### 3.1 类型系统中的能力

```rust
// ============ 能力模型的类型系统 ============ //

// ─── 能力类型定义 ───

/// 能力：线性资源 × 效应权限
/// 线性：不可复制、不可丢弃、必须消耗
/// 效应权限：允许执行的效应集合
pub struct Capability<P: EffectPermission> {
    /// 能力的唯一标识（线性保证）
    id: CapabilityId,
    
    /// 能力覆盖的资源
    resource: ResourceRef,
    
    /// 允许的效应（类型级追踪）
    permissions: P,
    
    /// 能力的来源（审计追踪）
    provenance: Provenance,
    
    /// 线性标记（编译期强制）
    linear_marker: PhantomData<*mut ()>,
}

/// 效应权限：能力允许的效应
pub trait EffectPermission {
    /// 允许的效应集合
    type AllowedEffects: EffectRow;
    
    /// 能力传递规则
    type TransferRule: TransferPolicy;
}

// ─── 具体能力示例 ───

/// 文件读取能力
pub struct ReadFileCapability {
    id: CapabilityId,
    resource: FilePath,
    permissions: ReadPermission,
    provenance: Provenance,
    linear_marker: PhantomData<*mut ()>,
}

/// 网络访问能力
pub struct NetworkCapability {
    id: CapabilityId,
    resource: UrlPattern,
    permissions: NetworkPermission,
    provenance: Provenance,
    linear_marker: PhantomData<*mut ()>,
}

/// 内存分配能力
pub struct MemoryCapability {
    id: CapabilityId,
    resource: MemoryRegion,
    permissions: MemoryPermission,
    provenance: Provenance,
    linear_marker: PhantomData<*mut ()>,
}

// ─── 能力的线性操作 ───

/// 能力传递（消耗旧的，产生新的）
pub fn transfer<C: CapabilityKind>(
    cap: linear C,
    to: EntityId,
) -> linear C {
    // 线性：旧的 cap 被消耗
    // 新的 cap 被产生
    // 类型系统保证：不能同时持有两个
    C::transfer(cap, to)
}

/// 能力使用（必须消耗）
pub fn use_capability<P: EffectPermission>(
    cap: linear Capability<P>,
    effect: P::AllowedEffects,
) -> Result<linear Capability<P>, CapabilityError> {
    // 使用能力执行效应
    // 能力被消耗但可以返回新的
    perform_with_capability(cap, effect)
}

/// 能力组合（产生更强的能力）
pub fn compose<A: CapabilityKind, B: CapabilityKind>(
    cap_a: linear A,
    cap_b: linear B,
) -> linear CombinedCapability<A, B> {
    // 能力组合 = 权限的并集
    // 线性：两个输入都被消耗
    CombinedCapability::from(cap_a, cap_b)
}

/// 能力分割（产生更弱的能力）
pub fn split<C: SplittableCapability>(
    cap: linear C,
) -> (linear C::First, linear C::Second) {
    // 能力分割 = 权限的拆分
    // 线性：输入被消耗，两个输出产生
    C::split(cap)
}
```

### 3.2 能力与效应系统的融合

```rust
// ============ 能力效应：你的原创融合 ============ //

// ─── 能力效应的定义 ───

/// 能力效应：需要特定能力才能执行的效应
effect CapabilityEffect<P: EffectPermission> {
    /// 使用能力执行效应
    authorized_effect(effect: P::AllowedEffects) -> Result<Value>,
    
    /// 请求新的能力
    request_capability(cap_type: CapabilityKind) -> linear Capability,
    
    /// 释放能力
    release_capability(cap: linear Capability) -> (),
}

// ─── Perform 需要能力 ───

fn read_file(path: FilePath) -> String | ReadFileCapability {
    // 需要持有 ReadFileCapability 才能 perform
    let content = perform ReadFileCapability::authorized_effect(Read { path });
    content
}

// ─── Handle 提供能力 ───

fn with_file_access<F, T>(f: F) -> T 
where F: Fn() -> T | ReadFileCapability
{
    handle f() {
        // Handle 提供 ReadFileCapability
        ReadFileCapability::authorized_effect(Read { path }) => {
            // 检查调用者是否有权限
            if has_permission(caller, path) {
                let content = perform_io_read(path);
                resume(Ok(content))
            } else {
                resume(Err(PermissionDenied))
            }
        },
        
        ReadFileCapability::request_capability(ReadFile) => {
            // 能力的授予逻辑
            let cap = grant_capability(ReadFileCapability::new(path));
            resume(cap)
        },
        
        ReadFileCapability::release_capability(cap) => {
            // 能力的释放逻辑
            revoke_capability(cap);
            resume(())
        },
    }
}

// ─── 能力在效应流形上的传播 ───

/// 能力流：能力在效应流形上的传播路径
pub struct CapabilityFlow {
    /// 能力的来源
    origin: CapabilityOrigin,
    
    /// 传播路径（效应流形上的路径）
    path: Vec<EffectPathSegment>,
    
    /// 当前持有者
    current_holder: EntityId,
    
    /// 能力的"相位"（使用状态）
    phase: CapabilityPhase,
}

/// 能力的"波粒二象性"（你的原创洞察）
pub enum CapabilityNature {
    /// 粒子性：能力作为离散的权限令牌
    Particle(CapabilityToken),
    
    /// 波动性：能力作为连续的权限场
    Wave(PermissionField),
    
    /// 叠加态：两者共存
    Superposition {
        token: CapabilityToken,
        field: PermissionField,
        interference: CapabilityInterference,
    },
}

/// 能力的干涉：多个能力共享资源
pub struct CapabilityInterference {
    /// 共享的资源
    shared_resource: ResourceId,
    
    /// 参与的能力
    capabilities: Vec<CapabilityId>,
    
    /// 干涉类型
    interference_type: InterferenceType,
}

// ─── 能力的"纠缠"：原子性保证 ───

/// 能力纠缠：多个能力操作的原子性
pub struct EntangledCapabilities {
    /// 纠缠的能力集合
    capabilities: Vec<CapabilityId>,
    
    /// 纠缠规则：AllOrNothing
    rule: EntanglementRule,
}

// 示例：文件系统的原子操作
fn atomic_file_operations() {
    // 纠缠的文件能力
    let entangled = EntangledCapabilities {
        capabilities: vec![
            read_file_cap,
            write_file_cap,
            delete_file_cap,
        ],
        rule: EntanglementRule::AllOrNothing,
        // 所有操作要么全部成功，要么全部失败

    handle entangled {
        // 使用纠缠能力执行原子操作
        perform AtomicFileOps::with_entangled(entangled) => {
            // 原子性由纠缠保证
            // 不是补偿，而是数学上的不可分割
            let result = atomic_execute(all_ops);
            resume(result)
        },
    }
}
```

### 4.1 能力生命周期管理

```rust
// ============ 能力的完整生命周期 ============ //

/// 能力状态机
pub enum CapabilityState {
    /// 未创建（潜在能力）
    Potential,
    
    /// 已创建（可用）
    Active,
    
    /// 已传递（在传播中）
    Transferred,
    
    /// 已使用（已消耗）
    Consumed,
    
    /// 已过期（生命周期结束）
    Expired,
    
    /// 已撤销（被授予权限收回）
    Revoked,
}

impl CapabilityState {
    /// 状态转换规则（类型系统强制）
    pub fn transition(&self, event: CapabilityEvent) -> Result<CapabilityState, TransitionError> {
        match (self, event) {
            (Potential, Create) => Ok(Active),
            (Active, Transfer) => Ok(Transferred),
            (Transferred, Receive) => Ok(Active),
            (Active, Use) => Ok(Consumed),
            (Active, Expire) => Ok(Expired),
            (Active, Revoke) => Ok(Revoked),
            _ => Err(InvalidTransition)
            // 线性类型保证：不会出现非法状态转换
        }
    }
}

/// 能力的来源追踪（审计）
pub struct Provenance {
    /// 初始授予者
    original_granter: EntityId,
    
    /// 传播链（完整的传播历史）
    transfer_chain: Vec<TransferRecord>,
    
    /// 时间戳
    timestamps: Vec<Timestamp>,
}
```

### 4.2 能力与模块系统的协调

```rust
// ============ 能力与模块的协调 ============ //

/// 模块能力接口：模块声明的所需能力
pub struct ModuleCapabilityInterface {
    /// 模块需要的能力
    required: Vec<CapabilityKind>,
    
    /// 模块提供的能力
    provided: Vec<CapabilityKind>,
    
    /// 能力传递策略
    transfer_policy: TransferPolicy,
}

/// 模块能力检查（编译期）
pub fn check_module_capabilities(module: &Module) -> Result<(), CapabilityError> {
    for required in &module.capability_interface.required {
        if !context_has_capability(required) {
            return Err(CapabilityError::MissingCapability {
                module: module.name(),
                capability: required,
                suggestion: "grant this capability at module initialization"
            });
        }
    }
    Ok(())
}

// ─── 示例：模块的能力声明 ───

module logger {
    // 声明需要的能力
    capability required {
        WriteCapability for stdout,
        WriteCapability for logfile,
    }
    
    // 声明提供的能力（其他模块可以获取）
    capability provided {
        LoggerCapability,
    }
    
    pub fn log(message: str) -> () | WriteCapability {
        perform WriteCapability::authorized(Write { target: stdout, data: message })
    }
}

// 调用者需要持有能力
module app {
    use logger;
    
    pub fn main(cap: linear WriteCapability) {
        // 必须持有 WriteCapability 才能调用 logger
        logger::log("Hello")
        // 编译器验证：cap 满足 logger 的能力需求
    }
}
```

## 七、总结

**2026 年的能力模型前沿是三个支柱的融合：线性类型（Rust 验证的工程可行性）、对象能力（OCap 的安全架构）、能力效应（与效应系统的深度集成）——而你的语言通过效应流形理论的独特视角，将能力从“静态权限管理”提升为“效应流形上的动态引导力”，这包括能力的传播路径、干涉模式、纠缠结构和波粒二象性——这是现有系统完全没有触及的深度。**

**你的能力模型的原创贡献**：能力不是与效应系统并列的独立安全机制，而是嵌入效应流形的“引导结构”——能力决定效应往哪里流、如何干涉、是否纠缠、能否坍缩——这使得安全不再是“检查清单”而是“流形的几何性质”。

```rust
// ============ 能力作为效应度规的语言表达 ============ //

// ─── 基础：能力门控效应（已有） ───

// Perform 需要能力（能力决定效应能否发生）
fn read_file(path: FilePath) -> String | ReadFileCap {
    let content = perform ReadFile(path);
    // ReadFileCap 是这个效应的"度规"
    // 它决定：效应可以/不可以发生
    content
}

// ─── 进阶：能力调制效应（新的理解） ───

// 能力不仅"允许/禁止"，还"调制"效应的性质
capability EffectMetric {
    // 度规系数：决定效应的传播性质
    fn metric_coefficient(
        effect: EffectKind, 
        dimension: Dimension
    ) -> f64;
    
    // 联络系数：决定效应的"弯曲"程度
    fn connection_coefficient(
        from: EffectKind, 
        to: EffectKind
    ) -> ConnectionMatrix;
    
    // 曲率张量：决定效应的"干涉"模式
    fn curvature_tensor(
        plane: (EffectKind, EffectKind)
    ) -> CurvatureTensor;
}

// ─── 具体示例：文件系统的能力度规 ───

capability FileSystemMetric: EffectMetric {
    // 读取能力的度规
    fn metric_coefficient(ReadFile, speed) -> f64 {
        1.0  // 全速读取
    }
    
    fn metric_coefficient(ReadFile, scope) -> f64 {
        0.5  // 只允许读一半文件（限制）
    }
    
    // 写入能力的联络
    fn connection_coefficient(ReadFile, WriteFile) -> ConnectionMatrix {
        ConnectionMatrix::sequential(
            read_then_write: 1.0,   // 允许读后写
            write_then_read: 0.0    // 禁止写后读
        )
    }
    
    // 删除能力的曲率（干涉）
    fn curvature_tensor((WriteFile, DeleteFile)) -> CurvatureTensor {
        CurvatureTensor::non_commutative(
            // 写和删除不对易
            // 顺序影响结果
            // → 存在干涉
            [Write, Delete] ≠ [Delete, Write]
        )
    }
}

// ─── 能力调制效应的具体表现 ───
```

```rust
// ============ 协同操作语义的精确定义 ============ //

/// 层次 1：门控（编译期，零开销）
pub fn gate_check(
    capability: &CapabilityType,
    effect: &EffectKind
) -> CompileTimeResult {
    // 编译期检查
    if capability.allows(effect) {
        CompileTimeResult::Allowed
    } else {
        CompileTimeResult::Error(
            "Effect requires capability: {}"
        )
    }
}

/// 层次 2：调制（运行时，度规查询）
pub fn modulate(
    capability: &CapabilityInstance,
    effect: EffectRequest
) -> EffectRequest {
    // 度规查询
    let metric = capability.metric(effect.kind);
    
    // 调制
    EffectRequest {
        kind: effect.kind,
        intensity: effect.intensity * metric.amplification,
        scope: restrict(effect.scope, metric.scope_limit),
        direction: redirect(effect.direction, metric.connection),
    }
}

/// 层次 3：演化（运行时，状态更新）
pub fn evolve_capability(
    capability: &mut CapabilityInstance,
    effect_used: &EffectRecord
) {
    // 能力的 on-effect 规则
    for rule in &capability.on_effect_rules {
        if rule.matches(effect_used) {
            rule.apply(capability);
            // 更新能力的状态
        }
    }
    
    // 检查衍生
    for derivation in &capability.derivations {
        if derivation.condition(capability) {
            capability.derive(derivation.new_capability);
        }
    }
}

/// 层次 4：耦合演化（运行时，迭代）
pub fn coupled_evolution(
    effect_computation: EffectComputation,
    initial_capability: CapabilityInstance,
    convergence: ConvergenceCriteria,
) -> Result<ConvergedState, DivergenceError> {
    let mut capability = initial_capability;
    let mut iteration = 0;
    
    loop {
        // Step 1: 效应沿当前度规传播
        let effect_result = propagate_with_metric(
            effect_computation.clone(),
            &capability
        );
        
        // Step 2: 度规被效应改变
        let new_capability = evolve_metric(
            &capability,
            &effect_result
        );
        
        // Step 3: 收敛检查
        if convergence.check(&capability, &new_capability) {
            return Ok(ConvergedState {
                final_capability: new_capability,
                final_effect: effect_result,
                iterations: iteration,
            });
        }
        
        // Step 4: 迭代
        capability = new_capability;
        iteration += 1;
        
        // 防止发散
        if iteration > convergence.max_iterations {
            return Err(DivergenceError::TooManyIterations);
        }
    }
}
```
